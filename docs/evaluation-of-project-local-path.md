# Kanboard 项目本地路径（project.path）功能价值评估报告

## 一、评估背景与问题提出

在 Kanboard 桌面看板系统中，每个项目（Project）均包含一个本地路径属性（`project.path`），支持用户在项目设置中配置本地工作区或代码库绝对路径。

随着 Kanboard 与 AI Agent（Antigravity、Cursor、Claude Code 等）协同流程的演进，团队提出了核心疑问：
**在当前人机协同研发模式下，项目本地路径是否有实际意义？是应当废弃精简，还是应当保留并强化？**

本报告基于当前代码实现、MCP 协议规范、Agent 协同流程及真实数据库采样数据，对该功能的设计定位、现实痛点、核心价值与后续演进路线进行系统评估。

---

## 二、当前实现与运行现状梳理

### 1. 技术链路全景

| 模块层级 | 当前实现方式 | 涉及文件 / 工具 |
| :--- | :--- | :--- |
| **数据存储层** | SQLite `projects` 表包含 `path TEXT NOT NULL DEFAULT ''` 字段 | `src-tauri/migrations/0006_project_path.sql` |
| **前端状态与仓库** | `Project` 与 `Task` 类型均维护 `path` 字段，支持响应式更新 | `src/types.ts`、`src/data/taskRepository.ts` |
| **交互与输入层** | 项目编辑弹窗提供纯文本输入框，无目录选择器，无合法性校验 | `src/components/ProjectEditor.vue` |
| **看板界面展示层** | 主看板、项目侧边栏、任务卡片、任务详情页**均未展示或消费**该路径 | - |
| **Prompt 生成层** | 拖拽或复制任务时若配置了路径，在所属项目后追加 `(path)` | `src/drag/agentPrompt.ts` |
| **MCP 工具层** | `get_task`、`list_projects` 返回路径；提供 `set_project_path` 工具 | `src-tauri/src/mcp.rs` |
| **SOP 规约层** | 规定 Agent 开展工作前需确认项目路径，未配置时可调用 MCP 工具反写 | `plugins/.../SKILL.md`、自定义 SOP |

### 2. 真实数据库采样分析

通过调用 MCP `list_projects` 工具对本地真实数据库进行抽样，当前系统中存在的 7 个活跃项目配置情况如下：

```text
1. medchat-edge-hardware     -> D:/ZhushiWorkspace/medchat-edge-hardware （已配置）
2. nmle-guide                -> D:\ZhushiWorkspace\nmle-guide            （已配置，反斜杠）
3. kanboard                  -> ""                                       （未配置）
4. clin-reasoning-question-gen -> ""                                     （未配置）
5. RAGLens                   -> ""                                       （未配置）
6. medchat-physician-exam    -> ""                                       （未配置）
7. medchat-edge              -> ""                                       （未配置）
```

- **高空置率**：7 个项目中仅有 2 个配置了本地路径，空置率达 **71.4%**。甚至核心工程 `kanboard` 自身路径亦为空。
- **格式不规范**：已配置的项目中，路径分隔符存在混用现象（正斜杠与 Windows 反斜杠并存）。
- **现象反映**：用户在日常使用中并未主动配置该路径，且即便不配置，现有功能流程也未受到阻断。

## 三、核心价值与现实局限多维剖析

### 1. 产生“鸡肋感”的核心原因（现实局限）

1. **与 IDE 宿主 Agent 的工作区上下文重叠**  
   在最常见的单项目开发场景中，用户通常先在 Cursor / Antigravity 中打开目标工程根目录，再与 Agent 对话。Agent 的宿主环境已自带当前工作目录（CWD）及 Active Workspaces。此时即便任务 Prompt 中携带了绝对路径，Agent 也仅在当前目录工作，该路径信息显得多余。

2. **桌面端缺乏消费闭环，人类用户无感知**  
   在 Kanboard 桌面端 UI 中，该字段仅仅静止地保存在项目编辑弹窗内。用户在看板中无法“一键打开项目文件夹”，无法“在终端中打开”，也无法“在 IDE 中打开”。对于不使用跨项目 Agent 的普通用户而言，该字段完全没有带来操作便利。

3. **配置成本高与输入体验原始**  
   项目编辑弹窗仅提供单行文本输入框，用户需要手动在操作系统文件管理器中寻找路径并复制粘贴。没有原生目录选择对话框，缺乏引导与存在性校验。

4. **绝对路径的脆弱性与多端同步冲突**  
   本地绝对路径深度依赖单一设备的磁盘盘符与目录结构（例如 Windows 盘符 `D:\...` 与 macOS 路径 `/Users/...`）。当用户在多设备间通过备份还原或云同步共享 SQLite 数据库时，绝对路径将失效并沦为脏数据。

---

### 2. 不可替代的核心架构价值（为什么不能废除）

尽管在当前单项目交互中存在上述局限，但从架构演进和全局任务调度视角来看，**项目本地路径具有战略意义**：

1. **Kanboard 作为“全局任务调度中枢（Task Hub）”的物理锚点**  
   Kanboard 不是某个单一代码仓库的内置插件，而是跨多个项目、跨业务条线的全局桌面看板。当面对多项目管理时，项目名称仅仅是逻辑标识，**`project.path` 是连接虚拟看板任务与本地物理磁盘工程的唯一确定性物理通道**。

2. **跨仓库与自动化 Agent（巡检、后台 Worker、多 Agent 团队）的刚需支撑**  
   当任务流转脱离单一 IDE 会话（例如调度一个全局守护 Agent 遍历各项目任务、执行每日构建、跑回归测试、或由一个 Super-Agent 跨仓库协同开发时），Agent 不具备预设的 CWD。Agent 必须通过 `get_task` 读取 `task.project.path`，才能准确切入对应目录并执行 `git`、构建与测试指令。

3. **本地桌面端（Tauri）差异化能力的重要抓手**  
   作为原生桌面应用，Kanboard 相较于 Web 看板最大的优势即是具备操作本地操作系统和文件系统的原生权限。一旦关联了本地路径，Kanboard 可以轻松实现“一键在 VS Code 打开”、“一键打开终端”、“一键打开文件资源管理器”，大幅提升开发者的日常流转效率。

4. **文档预览与附件引用的基础支撑**  
   Kanboard 具备 Markdown 本地文档预览能力（`document_preview`）。未来若任务说明或验证方案中需要引用项目工程内的相对路径文件（例如 `[架构设计](docs/arch.md)`），必须依赖 `project.path` 作为基准根路径方可实现解析与跨文件跳转。

## 四、评估结论与决策建议

### 1. 总体结论

| 评估维度 | 评估结论 |
| :--- | :--- |
| **是否应当废除？** | **坚决不建议废除。** 废除会导致 Kanboard 丧失作为本地工程调度中枢与自动化 Agent 协作的基础支撑。 |
| **现状评价** | **架构设计合理，但当前处于“半成品与轻度闲置”状态。** 痛点不在于字段本身多余，而在于“输入端难用”且“消费端未落地”。 |
| **处置策略** | **保留该字段，按“补齐输入体验 -> 落地桌面消费 -> 强化 Agent 规则”三步进行渐进式增强。** |

### 2. 收益与成本对比

```text
方案 A：彻底移除 project.path
- 收益：精简少量数据库字段与代码（约 50 行），降低少量认知成本。
- 代价：不可逆地切断全局看板对本地代码库的定位能力，自动化/跨项目 Agent 瘫痪，未来无法支持本地桌面快捷操作。
- 结论：得不偿失。

方案 B：保留并补齐闭环（推荐）
- 收益：完善开发者工作流，打通一键唤起 IDE / 资源管理器，消除 70%+ 的空置率，为多 Agent 自动化扫清障碍。
- 代价：仅需投入极小的前端与交互改造工作量（约半天至一天）。
- 结论：投产比极高。
```

## 五、演进改造路线（落地建议）

为彻底消除用户的“鸡肋感”，建议按以下四个递进阶段实施改造：

### 阶段一：输入体验升级（极小改动，解决空置率与输入繁琐问题）
- **原生目录选择**：利用 Tauri `plugin-dialog`，在 `ProjectEditor.vue` 输入框旁增加“浏览/选择文件夹”按钮，允许用户一键选取本地目录。
- **路径格式自动规范化**：保存时自动去除尾部斜杠，统一转换为标准格式。
- **存在性温和提示**：当检测到路径不存在时给出黄色叹号提示，但不强制阻断（兼顾跨设备数据流转）。

### 阶段二：桌面端消费场景落地（显著提升人类用户的使用价值）
- **项目快捷操作菜单**：在项目侧边栏（`ProjectSidebar.vue`）中，为已配置本地路径的项目增加右键菜单或快捷操作图标：
  - 【在文件资源管理器中打开】（调用系统 Shell）；
  - 【在 VS Code / 默认编辑器中打开】（调用 `code <path>`）；
  - 【在终端中打开】。
- **任务详情联动**：在任务详情页所属项目标签旁，支持悬浮查看路径并提供“打开所在目录”快捷入口。

### 阶段三：Agent 协同规范与跨目录调度优化
- **智能提示区分**：在 `agentPrompt.ts` 中，若生成提示词时检测到用户当前工作区与项目路径一致，可适度精简格式；若不一致或用于跨项目派工，明确强调工作区路径。
- **SOP 规则澄清**：在 SOP 中明确“单项目开发优先信任宿主 IDE 上下文；自动化与跨项目工作以项目配置路径为基准”，避免 Agent 在宿主工作区内做无谓的路径确认。

### 阶段四：跨设备与架构弹性支持（远期规划）
- 考虑引入工作区根路径环境变量或别名配置（例如 `$WORKSPACE_ROOT/kanboard`），方便同一数据库在不同开发设备（Windows / macOS / 个人机 / 办公机）之间平滑迁移。

---

## 六、总结

项目本地路径（`project.path`）是 Kanboard 区别于普通 SaaS 看板、建立“本地专属开发者中枢”的核心基础设施。当前其之所以显得意义不明显，根源在于功能闭环仅推进了一半。通过引入目录选择器并在桌面端提供一键唤起编辑器与文件夹等直观功能，能够以极低成本将这一“沉睡资产”激活为看板的核心亮点功能。
