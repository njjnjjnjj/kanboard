# Kanboard 任务执行 SOP

## 一、目的与适用范围

本 SOP 适用于不同项目和技术栈，约定 Agent 如何组织任务、同步进度、处理问题和交付成果。

Agent 负责自主推进已明确、已授权的工作；用户负责关键决策和最终验收。具体技术规范、执行命令和检查要求遵循项目约定与用户指令。

本 SOP 仅参考 karpathy-guidelines 中的任务理解、范围控制、步骤安排和验证闭环；代码实现方面的要求仍由该技能指导，不在本 SOP 中重复规定。

## 二、理解任务

开始执行前，读取任务详情、检查清单和必要上下文，明确：

- **目标**：需要解决什么问题，预期结果是什么。
- **范围**：本次需要完成哪些工作。
- **验收条件**：用户如何判断任务已经达到要求。

信息足以执行时，直接推进。一般实施细节由 Agent 自行判断；存在会明显影响结果的歧义时，向用户提出具体问题，并说明需要决定什么。

任务要求在本地项目中开展工作时，确认项目路径后再操作。仅讨论、调研或评审的任务，按其实际目标执行。

对于需求不明确的任务，与用户讨论并达成一致后，Agent 应及时将确认结果更新至任务说明，作为后续执行和验收的依据。

更新应整理为清晰的最终需求，包含必要的目标、范围、约束和验收条件，不直接堆贴聊天记录。尚未确定的事项明确标为待确认，不得将建议或假设写成已确认需求。

后续讨论改变原有约定时，同步修订任务说明，避免任务记录与实际执行不一致。

任务说明修订必须先读取 get_task，再调用 update_task_description，提交完整 Markdown 正文、简短 change_summary 和读取时的 expected_description；不得向正文追加时间戳日志。历史版本仅记录 Agent 通过 MCP 提交的修改，人工编辑不生成记录；通过 list_task_description_versions 查看单次修改前后差异，进度与阻塞备注独立记录。文档使用 Markdown 超链接，本机文档可用绝对路径。

## 三、组织与推进任务

开始实际工作后，将任务移入「进行中」，按以下原则组织工作：

1. **先明确结果**  
   将需求转化为可检查的完成条件，避免仅以“完成开发”“修复问题”等笼统描述作为目标。影响结果的重要假设应明确说明；存在关键歧义时，请用户决定。

2. **按复杂度安排步骤**  
   简单任务直接执行。多步骤任务列出简短计划，每一步说明要完成什么、如何确认完成；必要时同步到任务检查清单，不要求为每个操作建立子项。

   ```text
   1. 确认问题与预期结果 → 验证：能描述或复现当前行为
   2. 完成任务要求的调整 → 验证：满足对应完成条件
   3. 检查并提交验收 → 验证：结果和验收步骤清楚、可核对
   ```

   以上仅为组织示例，实际步骤根据任务调整。

3. **保持范围聚焦**  
   每个步骤都应服务于任务目标。发现无关问题时，简要记录；需要扩大范围时，先由用户确认。

4. **根据验证结果继续推进**  
   完成步骤后执行对应检查。未达到预期时，继续排查和调整；需要人工决策或外部条件时，按阻塞规则处理。无法执行的检查应记录原因，不得视为通过。

5. **保持计划与实际一致**  
   根据进展更新检查清单，在重要发现、方向调整或交付预期变化时同步用户。一般实施细节由 Agent 自主处理，无须逐步请求批准。

进度、检查清单和任务状态必须反映实际情况。

## 四、人工参与与阻塞处理

以下情况需要用户介入：

- 需求存在关键歧义，且不同选择会明显改变结果。
- 需要调整任务目标、范围或验收条件。
- 需要用户授权、提供资源或作出业务决策。
- 工作无法继续，且 Agent 已无法在授权范围内自行解决。

请求用户介入时，应简要说明：

1. 当前情况及其影响。
2. 已尝试的处理方式。
3. 需要用户决定或提供的内容；存在可选方案时，给出建议。

仅暂停受影响的部分，继续推进其他可独立完成的工作。任务整体无法继续时，记录阻塞原因并标记阻塞；条件解除后，再恢复执行。

用户在执行中提出补充或修正时，应及时纳入后续工作。若影响已完成内容或交付预期，明确说明。

## 五、检查与代码提交

交付前，按照任务目标和项目约定执行必要检查。检查力度应与改动影响相匹配，避免与任务无关的重复验证。

如实区分：

- 已完成的工作。
- 已执行的检查及其结果。
- 未执行或仍需人工验证的内容及原因。

不得将计划执行的检查写成已通过，也不得用检查清单勾选代替实际验证。

需要提交代码时：

- 仅提交与本任务相关的改动，保留用户已有工作。
- 提交信息使用 `feat:`、`fix:`、`refactor:`、`docs:` 等类型前缀，加简短中文描述。
- 示例：`fix: 修复任务状态更新异常`。

## 六、提测与人工验收

工作达到可供用户验收的状态后，调用 `submit_task_verification(task_id, content="完整 Markdown 正文")` 提交验证方案，由工具将任务流转至「待验证」。

验收方案由执行 Agent 根据任务类型、复杂度和实际交付成果自主编排，不强制统一章节、表格、复选清单或篇幅。内容应让用户清楚判断交付结果是否满足任务目标，并提供必要的核对方法；实际验证结果、未验证项和已知限制须如实说明，相关信息可自然合并，避免重复和无关内容。简单任务允许使用简短段落，复杂任务按需采用分节、列表、表格、代码块和截图。

以下仅说明不同任务可以如何组织内容，不是固定模板：

- 简单修复可简述调整结果、实际检查和验收操作。
- 界面调整可围绕操作路径、预期表现和实际截图组织。
- 调研分析可围绕结论、依据、交付文档和待决策问题组织。
- 复杂功能可按需要组织改动说明、验收场景和验证结果。

涉及网页、界面或其他视觉结果的任务，若 Agent 在自行校验过程中已生成或使用截图，应将相关截图一并附入验证方案，并简要标明对应页面、界面状态或验证点，方便用户核对。

截图应来自实际验证过程，效果图或设计稿不得作为实现结果的验证证据。

图片附件按以下方式提交：

1. 调用 `import_image_attachment(file_path="本机截图绝对路径")`，由 Kanboard 将图片复制到当前 SQLite 数据库同级的 `attachments` 目录，保留原文件。
2. 将工具返回的 `markdown` 或 `attachment.relativePath` 写入验证方案，使用 `![验证点](attachments/年/月/文件名.png)` 形式，并简要标明页面状态或验证点。
3. 图片引用不得使用项目绝对路径、`file://`、临时显示协议地址或仅存在于项目目录的相对路径。重新提测时，新增或更新后的截图也须重新导入；可复用内容未变的既有看板附件引用。
4. 若当前工具清单缺少 `import_image_attachment`，先刷新插件或 MCP 连接；仍不可用或导入失败时，说明原因并请求协助，不得改用项目绝对图片路径，也不得宣称图片已上传。

项目内的验证说明等文档可以保留本机文件超链接，例如 `[验证说明](/D:/项目/doc/验证.md)`，点击后由 Kanboard 的独立只读文档预览窗口打开。此约定适用于文档链接，图片仍须按上述附件流程导入。

本条不要求额外执行截图流程；没有截图时，如实说明实际验证方式即可。任务另有明确截图要求的，按任务要求执行。

Agent 不得自行将任务标记为「已完成」。最终完成状态由用户验收决定。

验收未通过时，依据反馈继续处理，更新验证方案后再次提测。反馈涉及新增需求或范围变化时，先由用户确认其归属与范围。

## 七、文档与沟通规范

以准确、简明、方便使用为原则：

- 简单内容使用短段落或清单。
- 对比关系适合表格时，再使用表格。
- 多行命令或代码使用带语言标签的代码块。
- 不堆砌单行长文本，不强制套用与任务无关的章节。
- 遵守中文文案排版规范，规范中英文、数字间空格和标点。
- 禁止使用 emoji。
- 所有完成情况、检查结果和任务状态均须真实，不夸大、不隐瞒未完成项。
